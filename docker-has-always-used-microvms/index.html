Docker has always used microVMs (well, since 2016)

There's a lot of buzz about "microVMs", where a workload runs with a stripped down Linux kernel, on a minimalist VMM such as firecracker on top of a hypervisor like KVM or Xen. MicroVMs are often contrasted to, and considered more secure than, traditional Linux Docker containers. What if I told you that Docker Desktop has always used microVMs? (since 2016)

Unikernels are microVMs

Unikernels can be considered an early form of microVM. Rather than booting a full Linux kernel on a full VMM, a unikernel links an app with only the drivers, filesystems and subsystems it actually needs; other code is omitted. For example a MirageOS unikernel app would have no processes, probably no filesystem, only one vCPU. Certainly no ssh or shell (unless you really want those). The VMM that hosts the Mirage unikernel was also minimal (see Solo5 and mirage-solo5 ). No legacy required. We were so confident in the security of the system that we ran a bitcoin pinata offering 10BTC to any hacker able to claim it. The BTC went unclaimed.

Boot can be really fast too: the "Just-In-Time Summoning of Unikernels" project (paper, code) optimized x86 VM creation time down to about 20ms (120ms on an underpowered 2015 ARM dev board)

The main (obvious) downside of unikernels is having to link your app with a bunch of kernel code. A lot of people would like to run existing Linux programs!

While we were developing Unikernels, Docker was busy inventing the modern form of Linux containers and revolutionising how software is built, shared and run. Docker acquired Unikernel Systems in 2016 and we combined the best of Unikernels (microVMs) and Linux containers into Docker for Mac (later Docker Desktop).

Brief timeline (some sequences may be shortened)

  1. 1990s
    Nemesis

    A vertically integrated OS: applications take responsibility for much of their own system code.

  2. Oct 2003
    Xen and the art of virtualization published

    The SOSP paper describes the Xen hypervisor, the foundation of the public cloud.

  3. Aug 2012
    Simon Crosby describes Bromium's micro-VMs

    Bromium's co-founder and CTO uses the term micro-VM for a hardware-isolated task, such as opening a document or browsing a web page, with access restricted to the resources it needs.

  4. Mar 2013
    MirageOS unikernels paper published

    The ASPLOS paper: compile an application and its OS libraries into a specialised VM image.

  5. Feb 2015
    Bitcoin Piñata security challenge launched [security challenge]

    10 BTC offered for breaking a MirageOS TLS unikernel. The bounty remained unclaimed in June’s review.

  6. May 2015
    MirageOS boots in as little as 20ms

    The Jitsu paper: boot an x86 unikernel on demand in response to a network request.

  7. 18 May 2015
    Intel Clear Containers described

    Lightweight VMs for container workloads: kvmtool on KVM, direct Linux boot without BIOS or UEFI, and virtio devices. Intel reports startup under 150ms with roughly 18–20MB of memory overhead.

  8. 21 Jan 2016
    Docker acquires Unikernel Systems

    The MirageOS and Xen expertise behind Unikernel Systems joins Docker.

  9. 24 Mar 2016
    Docker for Mac beta announced

    Uses a microVM system: Mirage libraries in the VMM, a minimal Linux kernel and minimal Linux userspace (later open-sourced as LinuxKit).

  10. 28 Jul 2016
    Docker for Mac generally available

    Containers run inside a minimal Linux VM, with HyperKit and MirageOS libraries on the host.

  11. 5 Dec 2017
    Kata Containers announced

    Combines Intel Clear Containers and Hyper's runV to run container workloads in lightweight VMs. In Kata's Kubernetes model, each pod runs in its own VM, with its containers sharing the guest Linux kernel.

  12. Nov 2018
    Firecracker announced at re:Invent

    AWS announces its minimal KVM-based VMM for serverless workloads.

  13. 2026
    Docker Sandboxes

    A separate locked-down microVM and Docker daemon for each coding agent session with support for governance.

A library VMM for Desktop applications

Our priority back then wasn't to add microVMs to Docker for their own sake. Instead our goal was to make Docker feel like a native app on Mac and Windows, rather than a bundle of components. Using our Mirage Unikernel libraries we started building a "library VMM": a VMM which could be embedded inside the Docker application, and which would be single purpose, minimal, secure and fast. The first version was called hyperkit (a fork of xhyve, itself derived from bhyve ). We linked the C code directly with the MirageOS block layer and used the Mirage userspace TCP/IP stack in a gvisor-like network stack vpnkit. The VMM code continues to evolve and is now called Docker VMM.1

The VM kernel and root filesystem were minimal too, based on the LinuxKit project. The current version is an even more slimmed down and efficient variant but conceptually the same, similar to containerd/nerdbox.

Docker for Mac in 2015-2016

For Docker for Mac (later renamed Docker Desktop) this allowed:

  • Running rootless on all platforms. Without requiring "rootless inside Linux": the whole Linux kernel is untrusted, so even a Linux CVE doesn't matter.
  • Minimal devices. We could carefully limit the host / VM interface, making it easy to understand and audit.
  • VPNs and network policy. It was easy to interoperate with VPNs, and to extend later to impose networking policy such as Registry Access Management.

And now in 2026

The Docker microVM tech is the foundation of both Docker Desktop and also Docker Sandboxes (why microVMs), where each sandbox runs in a separate microVM, completely isolated from each other and the host. Docker Sandboxes enables you to do things like run your favourite coding agent and harness securely, with strict isolation and governance.

To see what Docker microVM's can do, install Docker Sandboxes (sbx) and try `sbx run claude`.
